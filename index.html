CQYAPDREQ001 查詢復原承作明細

💡 前端手上的承作明細「少了幾筆」時，這支會去歷史紀錄（LOG 表）把每種承作方式最後一次的樣子撈回來，連同它的多階段利率一起打包，讓畫面可以「復原」。

項目 內容
交易代號 LIP-B-CQYAPDREQ001
API POST /common/applyDetail/queryRecover（CommonController）
進入方法 queryRecoverApplyDetail(req)
程式檔 svc/impl/CQYAPDREQ001SvcImpl.java（109 行）
上行 ApplyId 受理編號、ApplyDetailList 前端目前有的承作方式清單
下行 ApplyDetailList：要復原的承作明細，每筆底下掛 ApplyRateList 利率

架構圖

📖 白話：Controller 是櫃台，SvcImpl 是承辦員。承辦員自己不碰資料庫，而是把 SQL 檔名交給 SqlUtils（去檔案櫃拿 SQL 範本），再交給 SqlAction（真的跑去資料庫查）。

主流程

子流程：明細和利率怎麼配對

📖 白話：像把「訂單」跟「訂單明細」配對。每筆承作明細用 ApplyId + Type + ApplyForm + MainCreditKind 這 4 個欄位當作「身分證」（CQYAPDREQ001FormKey），利率也算出同一張身分證，就能用 computeIfPresent 一秒找到該掛在哪一筆底下；找不到的利率直接略過。

例外與重點

情境 結果
CLN_APPLY_DETAIL 查不到 DataNotFoundException「CLN_APPLY_DETAIL查無資料」
DB 筆數和前端筆數一樣 不需要復原，回空清單
LOG 表也查不到 回空的 ApplyDetailList（不報錯）
  • 只比筆數、不比內容：判斷有沒有缺，是用 size() 比較，不是逐筆比對承作方式。
  • N+1 查詢：每一筆明細都會再打一次 query_003，明細越多查詢次數越多。
  • query_002 固定只取 TYPE = 'B'、且 IS_ABOLISH is null（沒被作廢）的紀錄。

主流程

子流程：非同步錯誤怎麼還原

📖 白話：小幫手出錯時，錯誤會被裝進一個叫 CompletionException 的「外箱」。identifyException 負責拆箱，看裡面是哪一種錯，再原樣丟出去，讓上層照平常的方式處理。
