CQYAPDREQ001 查詢復原承作明細

💡 前端手上的承作明細「少了幾筆」時，這支會去歷史紀錄（LOG 表）把每種承作方式最後一次的樣子撈回來，連同它的多階段利率一起打包，讓畫面可以「復原」。

項目 內容
交易代號 LIP-B-CQYAPDREQ001
API POST /common/applyDetail/queryRecover（CommonController）
進入方法 queryRecoverApplyDetail(req)
程式檔 svc/impl/CQYAPDREQ001SvcImpl.java（109 行）
上行 ApplyId 受理編號、ApplyDetailList 前端目前有的承作方式清單
下行 ApplyDetailList：要復原的承作明細，每筆底下掛 ApplyRateList 利率

架構圖

📖 白話：Controller 是櫃台，SvcImpl 是承辦員。承辦員自己不碰資料庫，而是把 SQL 檔名交給 SqlUtils（去檔案櫃拿 SQL 範本），再交給 SqlAction（真的跑去資料庫查）。

🧰 工具在做什麼

工具 比喻 在這支 API 做什麼
SqlUtils 檔案櫃 用檔名取出 resources/sql/ 裡的 SQL 範本
SqlAction 跑腿 拿 SQL 和參數 paramMap 真的去資料庫查。queryForList 回 List<Map>（query_001），queryForListVO 直接回物件（query_002、003）
ObjectMapper 轉換器 把查到的利率 FormValueVO 轉成下行要的 ApplyRate 物件，只留 10 個欄位
NormalResponseFactory 包裝員 把整理好的結果包成統一的回應格式 ResponseTemplate，每支 API 回給前端的外框都長一樣

🗄️ 資料表存什麼

資料表 存什麼 這支 API 拿來做什麼
CLN_APPLY_DETAIL 目前的承作明細，一種貸款一列 query_001：只拿 A 版來數有幾筆
CLN_APPLY_DETAIL_LOG 承作明細的歷史紀錄，每次異動多存一列 query_002：每種承作方式取最新一筆，就是要復原的明細
CLN_APPLY_RATE_LOG 分段利率的歷史紀錄 query_003：每筆要復原的明細各查一次它的利率
CLN_RD_COMMON_CODE 代碼字典：每種代碼對應的中文名稱 JOIN 進來，把代碼翻成中文

主流程

子流程：明細和利率怎麼配對

📖 白話：像把「訂單」跟「訂單明細」配對。每筆承作明細用 ApplyId + Type + ApplyForm + MainCreditKind 這 4 個欄位當作「身分證」（CQYAPDREQ001FormKey），利率也算出同一張身分證，就能用 computeIfPresent 一秒找到該掛在哪一筆底下；找不到的利率直接略過。

SQL 流程

📖 白話：三支 SQL 像三道工序。query_001 先「點名」現在有幾筆；query_002 去歷史檔案櫃，每種承作方式只拿最新的那一張；query_003 再替每張明細把利率的最新版本找回來。圖裡每個方塊的小字 💬 是白話說明，⚠️ 是要注意的地方。

query_001：目前的承作明細（只拿來數筆數）

query_002：從明細 LOG 取每種承作方式的最新一筆

query_003：單一承作方式的利率 LOG（每筆明細各跑一次）

SQL 主表 篩選重點 一次取幾筆
query_001 CLN_APPLY_DETAIL TYPE = 'A' 全部承作方式
query_002 CLN_APPLY_DETAIL_LOG TYPE = 'B'、沒作廢、STATUS = 'D'、最新 每個 APPLY_FORM 1 筆
query_003 CLN_APPLY_DETAIL_LOG ⨝ CLN_APPLY_RATE_LOG 同上，再加 :ApplyForm 每個起期 1 筆
  • query_001 用 TYPE = 'A'，query_002／003 用 TYPE = 'B'：比的是 A 版的筆數，復原的是 B 版的 LOG。
  • query_001 的別名寫成 ACNT_CODE__WMA_NAME（兩個底線），query_002 是 ACNT_CODE_WMA_NAME。這支只拿 query_001 數筆數，所以沒影響；別的地方要沿用時要注意。

資料結構示意

📖 白話：下面的值都是假資料，只是用來看形狀。List 像一排置物櫃，照順序放；Map 像一排有名牌的信箱，用「鑰匙（key）」找到「內容（value）」。橘色方塊是鑰匙，白色方塊是內容，💬 是這個值在業務上代表什麼。

🔎 符號怎麼看

  • [0]、[1]、[2]：List 的第幾格。程式是從 0 開始數，所以 [0] 是第 1 格、[1] 是第 2 格。
  • 「A001」：格子或信箱裡裝的值，「」裡面就是實際的文字。
  • [ …, … ]：把一整個 List 的內容寫在同一行，例如 [ 第 1 期起, 第 13 期起 ] 代表這個 List 有 2 格。
  • { 鑰匙: 值, … }：把一整個 Map 寫在同一行，冒號左邊是鑰匙、右邊是內容。
  • ( A001, B, 1, 1 )：一把 FormKey，括號裡依序是 ApplyId、Type、ApplyForm、MainCreditKind 這 4 個欄位的值。

資料結構示意

📖 白話：下面的值都是假資料。這支的重點是「換形狀」：把別支 API 回來的扁平清單，依承作方式分組、再組成報表一列一列要的文字。橘色方塊是 Map 的鑰匙，白色方塊是內容，💬 是這個值在業務上代表什麼。

🔎 符號怎麼看

  • [0]、[1]、[2]：List 的第幾格。程式是從 0 開始數，所以 [0] 是第 1 格、[1] 是第 2 格。
  • 「A001」：格子或信箱裡裝的值，「」裡面就是實際的文字。
  • [ …, … ]：把一整個 List 的內容寫在同一行，例如 [ 第 1 期起, 第 13 期起 ] 代表這個 List 有 2 格。
  • { 鑰匙: 值, … }：把一整個 Map 寫在同一行，冒號左邊是鑰匙、右邊是內容。

怎麼對照左邊的圖

圖上 JSON 裡
ReportId 方塊 "ReportId"，報表代號
灰框 DetailList "DetailList": [ … ]
橘框 [0]、[1] DetailList 裡的每一個 { … }，報表上一種貸款一列
黃框 ParamMap "ParamMap": { … }，裡面只有 DetailStr
框線顏色 左右兩邊同一個顏色就是同一塊資料
  • 值都是假資料。欄位名稱是照程式的 @JsonProperty 寫的。
  • DetailList 每一列是 Map<String, String>，所以鑰匙是程式裡寫死的大寫名稱（例如 APPLY_FORM_NM），值全都是字串。
  • JSON 裡的 \n 是換行，報表印出來會分成好幾行，例如 LIMIT_SHOW 會印成「20年／寬限期／2年」三行。
  • Map 的鑰匙順序不固定（HashMap），實際回傳的順序可能和這裡不一樣，不影響使用。
  • 整包回應外面還會再包一層 ResponseTemplate（表頭 MwHeaderResponse + 這份內容 tranrs），外框在 JSON 裡的鑰匙名稱要看共用函式庫，這個專案裡查不到。
